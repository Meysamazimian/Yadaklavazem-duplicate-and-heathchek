# Yadaklavazem · Duplicate & Health-check

اپ مستقل و جدا از بک‌اند که روی همان سرور cPanel اجرا می‌شود و دو کار می‌کند:

1. **دوپلیکیت دیتابیس (فقط‌اضافه‌کردنی):** هر چند دقیقه یک‌بار ردیف‌های جدید دیتابیس اصلی را در یک دیتابیس دوم کپی می‌کند. هیچ‌چیز حذف یا بازنویسی نمی‌شود.
2. **مانیتورینگ اندپوینت‌ها:** در همان چرخه همه‌ی مسیرهای GET بک‌اند را (از روی OpenAPI خود بک‌اند) چک می‌کند و در یک داشبورد فارسی (راست‌به‌چپ) و رمزدار نشان می‌دهد.

Stack مثل بک‌اند: Node + TypeScript + Express + Knex (mysql2).

## چطور کار می‌کند

یک «چرخه» = دوپلیکیت + چک سلامت، هم‌زمان. چرخه با **زمان‌بند داخلی** (هر `CYCLE_INTERVAL_MINUTES` دقیقه) یا با **هیت کرون** (`/cron/run`) یا با دستور `npm run cycle` شروع می‌شود. قفل داخل دیتابیس جلوی اجرای هم‌زمان دو چرخه را می‌گیرد (حتی اگر Passenger چند پروسس بالا بیاورد).

### دوپلیکیت
- جدول‌های دیتابیس مبدأ از `information_schema` خوانده می‌شوند. جدول‌ای که در مقصد نیست از روی `SHOW CREATE TABLE` ساخته می‌شود (بدون FOREIGN KEY تا ترتیب کپی مهم نباشد).
- ستون جدیدی که در مبدأ اضافه شده باشد به مقصد هم اضافه می‌شود؛ enum و varchar فقط **بزرگ‌تر** می‌شوند، هیچ ستونی حذف یا کوچک نمی‌شود (سازگار با `repairMissingColumns` بک‌اند).
- جدول با کلید اصلی عددی تک‌ستونه: روش `pk-incremental`. آخرین id کپی‌شده (watermark) ذخیره می‌شود و فقط `id` بزرگ‌تر خوانده می‌شود، با `REPLICATE_LOOKBACK` ردیف اطمینان برای تراکنش‌هایی که دیرتر commit شده‌اند.
- جدول با کلید اصلی دیگر (مثلاً رشته‌ای یا چندستونه): روش `full-scan` (هر چرخه کل جدول با کلید صفحه‌بندی می‌شود، تا سقف `FULL_SCAN_MAX_ROWS`).
- جدول بدون کلید اصلی «ردشده» علامت می‌خورد (کپی امن فقط‌اضافه‌کردنی ممکن نیست).
- همه‌ی نوشتن‌ها `INSERT IGNORE` است؛ هیچ `UPDATE`/`DELETE`ای روی داده‌ی کپی‌شده اجرا نمی‌شود. روی مبدأ فقط `SELECT`/`SHOW` اجرا می‌شود.
- **محدودیت:** ردیفی که در مبدأ *ویرایش* شود در کپی به‌روز نمی‌شود (فقط ردیف تازه اضافه می‌شود). این رفتار عمدی است.
- هر اجرا (تعداد ردیف، مدت، خطا، ردیف عقب‌مانده) و وضعیت هر جدول ثبت می‌شود.

### مانیتورینگ
- مسیرهای بدون پارامتر `GET` از `BACKEND_URL + BACKEND_SWAGGER_PATH/spec/{storefront,admin,admin-sales,platform}.json` پیدا می‌شوند و هر `DISCOVERY_REFRESH_MINUTES` دقیقه تازه می‌شوند. مسیر `GET /health`، `GET /api/health` و `GET /` همیشه با انتظار `200` چک می‌شوند.
- درخواست‌ها هدر `X-Internal-Token` و `X-Forwarded-Host` (از `MONITOR_SHOP_HOST`) دارند تا از تشخیص فروشگاه بگذرند.
- برای مسیرهای دیده‌شده انتظار پیش‌فرض `<500` است: بدون توکن، پاسخ ۴۰۱/۴۰۳ یعنی لایه‌ی احراز هویت زنده است. فقط ۵xx، تایم‌اوت و قطع اتصال «خراب» حساب می‌شود.
- مسیرهای ربات تلگرام، بازگشت درگاه پرداخت و خروج پیش‌فرض بررسی نمی‌شوند (`MONITOR_EXCLUDE`)؛ چون ورود اشتباه ربات قفل می‌کند و بازگشت درگاه می‌تواند اثر جانبی داشته باشد.
- پس از `FAIL_THRESHOLD` شکست پشت‌سرهم رویداد «قطع» و پس از برگشتن رویداد «وصل» ثبت می‌شود.

### فایل اختیاری اندپوینت‌ها (`ENDPOINTS_FILE`)
```json
[
  { "path": "/api/products", "expect": "200", "bodyContains": "\"ok\":true",
    "headers": { "Authorization": "Bearer ..." } },
  { "path": "/api/admin/orders", "expect": "200,401" }
]
```
`expect` می‌تواند `200`، `200,204`، `2xx` یا `<500` باشد. مقدار هر مسیر با کلید یکسان، مقدار پیدا‌شده را بازنویسی می‌کند. متد پیش‌فرض GET است.

## راه‌اندازی روی cPanel

1. در cPanel یک **دیتابیس خالی دوم** و یک کاربر MySQL برایش بسازید (مقصد دوپلیکیت). برای مبدأ ترجیحاً کاربر **فقط‌خواندنی** (SELECT) بسازید.
2. کد را در یک پوشه‌ی جدا بگذارید (مثلاً `~/healthcheck`)، سپس در ترمینال: `npm install && npm run build`.
3. **Setup Node.js App**: Application root = همان پوشه، Startup file = `server.js`، نسخه‌ی Node ‏18 به بالا. متغیرهای محیطی را از `.env.example` وارد کنید (یا فایل `.env` بسازید). پس از ذخیره، Restart کنید.
4. داشبورد روی همان دامنه/ساب‌دامنه‌ای که برای اپ تعیین کرده‌اید باز می‌شود؛ با `DASHBOARD_PASSWORD` وارد شوید.
5. **کرون (توصیه می‌شود):** cPanel معمولاً پروسس بی‌کار را می‌خواباند و زمان‌بند داخلی هم با آن می‌خوابد. یک Cron Job هر ۵ دقیقه اضافه کنید، یکی از دو روش:
   - هیت: `*/5 * * * * curl -s -H "x-cron-key: <CRON_KEY>" https://YOUR-DOMAIN/cron/run >/dev/null` (با `CRON_KEY` تنظیم‌شده؛ پاسخ فوراً `202` است و چرخه در پس‌زمینه اجرا می‌شود؛ `?force=1` برای اجرای فوری، `?wait=1` برای منتظر ماندن). کلید فقط از هدر `x-cron-key` پذیرفته می‌شود؛ `?key=` جواب 404 می‌گیرد، چون کلیدِ داخل نشانی در لاگ دسترسی هاست می‌ماند.
   - مستقیم: `*/5 * * * * cd ~/healthcheck && /path/to/node dist/cycle.js` (نیاز به `.env` در همان پوشه؛ `--force` برای نادیده‌گرفتن فاصله)
   
   اگر فقط کرون را می‌خواهید `ENABLE_SCHEDULER=false` بگذارید. اجرای هم‌زمان هر دو بی‌خطر است.

### متغیرهای محیطی
همه در `.env.example` با توضیح آمده‌اند. مهم‌ترها:

| متغیر | معنی |
| --- | --- |
| `SRC_DB_*` | دیتابیس اصلی (فقط خواندن) |
| `DST_DB_*` | دیتابیس کپی (باید با مبدأ فرق داشته باشد؛ در غیر این صورت اپ بالا نمی‌آید). خالی‌بودن host/user/password یعنی همان مقدار `SRC_*` |
| `DASHBOARD_PASSWORD` | رمز داشبورد (الزامی، حداقل ۱۲ کاراکتر) |
| `SESSION_SECRET` | راز امضای نشست (الزامی، حداقل ۳۲ کاراکتر تصادفی، مثلاً `openssl rand -hex 32`). بدون آن اپ بالا نمی‌آید |
| `CYCLE_INTERVAL_MINUTES` | فاصله‌ی چرخه، پیش‌فرض ۵ |
| `CRON_KEY` | کلید `/cron/run` (خالی = غیرفعال؛ در غیر این صورت حداقل ۳۲ کاراکتر) |
| `BACKEND_URL` | آدرس بک‌اند از دید همین سرور |
| `INTERNAL_PROXY_TOKEN` | همان مقدار بک‌اند |
| `MONITOR_SHOP_HOST` | هاست یک فروشگاه واقعی برای مسیرهای فروشگاهی |
| `REPLICATE_EXCLUDE` / `REPLICATE_INCLUDE` | جدول‌هایی که کپی نشوند / فقط همین‌ها کپی شوند. پیش‌فرض `REPLICATE_EXCLUDE`: `refresh_tokens,otp_codes,rate_limits,idempotency_keys,cache,jobs,knex_migrations_lock` |
| `RETENTION_DAYS` | نگهداری تاریخچه‌ی مانیتورینگ (پیش‌فرض ۱۴ روز) |

**چرا این جدول‌ها کپی نمی‌شوند:** نشست‌ها، کدهای ورود، شمارنده‌های محدودیت نرخ، کلیدهای idempotency، cache و صف کارها ارزش پشتیبان ندارند و کپی‌شان فقط جای دومی برای دزدیده‌شدن نشست و کد ورود می‌سازد. دیتابیس دوم هم کپی بقیه‌ی داده‌هاست، پس باید همان محافظت دیتابیس اصلی را داشته باشد: کاربر MySQL جدا با رمز جدا، و بدون دسترسی از راه دور (Remote MySQL خاموش).

داشبورد هدر CSP سخت‌گیر می‌فرستد و ورود را برای هر IP بعد از ۵ تلاش ناموفق، و برای همه بعد از ۲۰ تلاش ناموفق در ۱۵ دقیقه، ۱۵ دقیقه قفل می‌کند.

جدول‌های خود اپ با پیشوند `__dup_` و `__mon_` در دیتابیس مقصد ساخته می‌شوند. فقط تاریخچه‌ی مانیتورینگ قدیمی (بیش از `RETENTION_DAYS`) پاک می‌شود؛ داده‌ی کپی‌شده هرگز.

## داشبورد
خلاصه (وضعیت، آپتایم ۲۴ ساعته، نمودار تأخیر، آخرین دوپلیکیت و lag)، فهرست اندپوینت‌ها با نمودار کوچک و تاریخچه‌ی هر کدام، اجراهای دوپلیکیت و وضعیت هر جدول، و رویدادها. دکمه‌ی «اجرای هم‌اکنون» یک چرخه را فوراً شروع می‌کند. صفحه هر ۳۰ ثانیه تازه می‌شود.

## توسعه
```bash
cp .env.example .env     # مقادیر را پر کنید
npm install
npm run dev              # اجرای توسعه
npm run lint             # tsc --noEmit
npm test
npm run build
```

## گیت‌های امنیتی CI

workflow `.github/workflows/ci.yml` روی هر push و PR این‌ها را چک می‌کند:

- **تست و تایپ**: `npm run lint` و `npm test`.
- **وابستگی‌ها** (`scripts/ci/audit.js`): هشدار high یا critical در `npm audit --omit=dev` قرمز می‌شود. استثنا فقط در `security/audit-allowlist.json` با شناسه‌ی GHSA، دلیل و تاریخ انقضا (حداکثر ۹۰ روز).
- **workflowها** (`scripts/ci/pinned-actions.js`): هر action با sha کامل commit سنجاق شده و هر workflow `permissions` صریح دارد.
- **رازها** (job `secrets`، gitleaks): کل تاریخچه‌ی git.
- **تحلیل ایستا** (job `sast`، `scripts/ci/semgrep.sh`): قاعده‌های امنیتی Semgrep از یک commit ثابت. یافته‌ی اشتباهی فقط روی همان خط با `// nosemgrep: <rule-id> -- دلیل` ساکت می‌شود.

این ریپو دیپلوی خودکار ندارد؛ فقط کدی را روی هاست بگذارید که CI آن سبز است. PRهای Dependabot (`.github/dependabot.yml`) را هم فقط وقتی merge کنید که CI سبز است.
